## 1. Загальний огляд виконаної роботи (Milestone 1)

У межах першого майлстоуну Lab 05 реалізовано фундамент багатокористувацької клієнт-серверної мережевої архітектури з **авторитетним сервером (Authoritative Server)**:

1. **Спільний воркспейс `shared/`:**
   - Створено третій ізольований npm-пакет `shared/` (`workspaces: ["client", "server", "shared"]`).
   - Симуляція (`sim/`) повністю очищена від DOM/Canvas/Node-специфічних залежностей та є ізоморфною.
   - Реалізовано детермінований псевдовипадковий генератор `mulberry32` із зерном (`shared/src/prng.js`).
   - Створено схему протоколу версії 1 (`shared/src/protocol/index.js`) та шар серіалізації `JsonCodec` (`shared/src/codec/index.js`).

2. **Авторитетний серверний цикл симуляції `Match` (30 Hz):**
   - Реалізовано прецизійний таймер на базі абсолютного цільового часу (`nextTick += intervalMs; setTimeout(tick, nextTick - performance.now())`) замість `setInterval` для усунення часового дрейфу.
   - Сервер валідує вхідні команди клієнтів (`turn` обмежено діапазоном `[-1, 1]`, булеві прапорці `thrust`, `reverse`, `fire`).
   - Сервер регулярно (30 разів/с) розсилає знімки світу (`snapshot`) із номером поточного тику та підтвердженням останньої обробленої команди кожного гравця (`lastProcessedSeq`).
   - Додано ендпоінт телеметрії `GET /api/stats` із показниками середньої тривалості тику та джиттера (`avgTickDurationMs`, `avgTickJitterMs`).

3. **Клієнт без локального передбачення (Dumb Client):**
   - Клієнт щокроку відправляє пакет введення з монотонним номером черги `{ seq, tick, thrust, reverse, turn, fire }` та зберігає його у буфері `pendingInputs`.
   - За вимогами Milestone 1 передбачення відключено: положення корабля змінюється виключно після отримання авторитетного `snapshot` від сервера.

4. **Інжектор штучної затримки та оверлей Netgraph:**
   - На сервері та клієнті впроваджено симулятор затримки (`delayMs`), джиттера (`jitterMs`) та втрати пакетів (`dropRate`), керований повідомленням `admin_latency`.
   - На фронтенді додано напівпрозорий оверлей **Netgraph**, який у реальному часі відображає:
     - `RTT` (через пінгування `ping`/`pong`);
     - `Server Tick` (частота 30 Hz);
     - `Snap Age` (вік останнього знімка);
     - `Bandwidth` (вхідний та вихідний трафік у KB/s);
     - `Pending Inputs` (кількість непідтверджених команд у польоті);
     - `Reconciliation` (`0.0 px (No Pred)`).
     - Кнопки швидких пресетів (`0 ms`, `50 ms`, `100 ms`, `150 ms + Jitter`) та повзунки точного налаштування.

## 2. Результати перевірки та тестів

### 2.1. Автоматизоване тестування
- **Детермінізм симуляції (`server/test/shared-sim.test.js`):**
  - Підтверджено завантаження `shared` у чистому середовищі Node.js без об'єктів `window` / `document`.
  - 1 000 кроків симуляції з однаковими входами збігаються біт-у-біт (`SHA-256` хеш ідентичний).
  - Введення невеликого шуму (`Math.random()`) негайно порушує детермінізм і змінює хеш.
- **Серверний матч і затримка (`server/test/match.test.js`):**
  - Успішна робота циклу 30 Hz та збір статистики через `GET /api/stats`.
  - Коректне врахування `lastProcessedSeq` у знімках сервера.
  - Динамічне налаштування інжектора затримки через `admin_latency`.
- **Загальний результат:** Усі **37 тестів бекенду** (`npm test`) та **клієнтські тести** (`npm run test:client`) проходять успішно. Перевірка коду `npm run check` (ESLint + Prettier) — **0 помилок**.

## 3. Експеримент: Поведінка Dumb Client при затримці 100 мс

За інструкцією M1 протестовано роботу з фіксованою затримкою 100 мс:

| Показник Netgraph | Пресет 0 ms (LAN) | Пресет 100 ms (M1) |
| :--- | :--- | :--- |
| **RTT (Round-Trip Time)** | ~1–3 мс | ~200–208 мс (100 мс в один бік) |
| **Вік знімка (Snap Age)** | ~30–33 мс (30 Hz) | ~30–34 мс (періодичність збережена) |
| **Черга непідтверджених входів (Pending Inputs)** | 1–2 пакети | **6–8 пакетів** |
| **Відчуття керування (Feel)** | Миттєве | Відчутний «ватний» лаг: корабель реагує через ~100–120 мс після натискання клавіші |
| **Зсув передбачення (Correction)** | 0.0 px | 0.0 px (передбачення вимкнено) |

**Висновки:**
Без клієнтського передбачення (Client-Side Prediction) навіть помірна мережева затримка у 100 мс робить динамічний догфайт вкрай некомфортним, оскільки гравець бачить наслідок натискання кнопки лише через повний цикл RTT. Це практично доводить необхідність реалізації механізмів **Prediction & Server Reconciliation** у Milestone 2.
